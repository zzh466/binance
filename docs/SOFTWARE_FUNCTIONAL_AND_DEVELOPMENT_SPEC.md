## 1. 定位、范围与最高优先级约束

### 1.1 软件定位

本软件是面向新期管理端账号下所选 Binance 子账号的 U 本位交易客户端。主要用途包括：

- 查询合约行情、最新成交价和当前有限档盘口。
- 使用表单、主行情图双击、可配置快捷键快速下单。
- 撤销、查询和修改委托，观察已确认的自有挂单。
- 实时维护订单、实际成交、交易回合、账户收益和持仓。
- 通过“当前持仓”及“一键平所有”辅助用户在休息或退出前控制敞口。
- 将所选 Binance 账号的交易资金指标定期同步到新期管理端。
- 支持同一电脑多实例、开发热更新以及 macOS/Windows 运行和分发。

### 1.2 当前范围

- 只创建 U 本位客户端，`marketType` 为 `futures`。
- 显式传入现货市场类型应被拒绝，而不是静默自动路由。
- 固定使用单向持仓，不提供用户切换双向持仓的入口。
- 只操作当前 API Key 所属的一个 Binance 账号，不代表主账号下所有子账号。
- 新期管理端用户可以拥有多个 Binance 账号，但进入主窗口前选定其中一个。
- WireGuard、DNS、系统代理和网络路由由操作系统负责，代码中没有 SOCKS5 隧道配置。

### 1.3 不能被优化或重构破坏的规则

1. **订单、持仓和盈亏的权威来源是 Binance，不是鼠标点击、按键动作或本地预测。**
2. 主图挂单必须在 Binance 确认后才出现，收到确定的成交/撤单终态后才消失。
3. 真实下单已写入 WebSocket、但响应丢失时，不得盲目通过 HTTP 再下同一笔。
4. 下单不明确应使用 `UNKNOWN` 并查询确认，不得假装失败后自动新建第二笔。
5. 查询失败、数据结构异常、快照过期，不得被解释为“已确认无持仓”。
6. 交易回合完成是本地成交配对结果，不能替代 Binance 全账号持仓确认。
7. 开仓和平仓含义必须保留；明确平仓必须使用 `reduceOnly` 等减仓保护。
8. API Secret、管理端原始账号凭证不得下发到页面、写入功能配置或提交 Git。
9. 普通表单、快捷键和鼠标下单必须共享底层下单、安全校验和 LinkID 逻辑。
10. 切换合约、环境或账号后，旧异步返回不得污染新范围的数据。
11. macOS 与 Windows 是共同支持目标，不得为了一个平台破坏另一个平台。
12. “优化低延迟”不授权绕过证书校验、流控、单向持仓、订单确认或防重复规则。

### 3.3 分页和尺寸

- `tablePagination.js` 是通用十行分页实现，包括登录后的账号选择列表。
- 列表每页最多10条业务数据；占位提示不是业务数据。
- 分页控制应显示页码/总条数，并提供翻页；数据减少时要修正越界页码。
- 分页隐藏其他页的行，不应删除其业务状态。
- 页面采用暗色样式、列表横向滚动和内容区布局约束，避免长列表撑高窗口。
- 主窗口默认1080×820，可调整大小，不设置阻止缩小的主窗口最小高度。
- Canvas 本身为980×300的基准绘图区域；“可以缩小主窗口”不等于所有图像自动按比例缩成任意尺寸。
- 点击页面重新加载不应产生下单、平仓或自动交易。

| 当前持仓 | 刷新当前持仓 | 独立快速全账号持仓复核，不等待收益历史 |

```text
  → 自动连接账户事件、账户/持仓刷新和管理端同步
  → 页面初始化并连接默认全局合约行情
```

### 4.2 管理端登录

管理端基址由 `MANAGER_API_BASE_URL` 定义：

`http://139.196.41.155:8082/vtpmanagerapi`

登录使用 `POST /access/loginClientDAT`：

```json
{
  "userNm": "用户在窗口中输入的用户名",
  "userPwd": "用户在窗口中输入的密码",
  "appVersion": "990812b",
  "userMAC": "00:1c:42:d4:1b:33"
}
```

上面的 MAC 只表示格式，不是强制使用该地址。正式逻辑从当前电脑网卡读取。文档、测试样例和源码均不应新增真实用户密码。

### 4.3 MAC选择

- 来源：`os.networkInterfaces()`，排除内部回环与非法/全零MAC。
- 规范化为小写、冒号分隔的六段地址，兼容Windows返回的连字符。
- 优先级：中文“以太网”“以太网2”…；其次英文Ethernet系列；其次macOS `en0/en1`；普通网卡与Wi-Fi随后；WireGuard/VPN/虚拟网卡较低。
- 同优先级按名称和MAC排序，避免随机选取。
- 没有有效网卡时需要明确报错，不能默默提交空值。

### 4.4 账号合并和选择

- 登录接口与 `/user/info` 均返回 `futureAccountVOList`，字段名称存在大小写/别名差异。
- 程序通过API Key身份（`futureInvestorId` 等字段的归一化值）合并，而不是仅用 `futureUserName`。
- 登录返回的账号 `id` 用于管理端资金同步；用户信息接口中的丰富属性补充到同一账号。
- 当前API Key按 `getAccountApiKey()` 统一解析；Secret来自 `futureUserPwd`。
- 多账号选择页面展示账号名称；确认后主进程解析具体选项并验证凭证。
- 同名账号不应被直接当成同一个账号；当前仍有同名展示标记的边界，见第24节。
- 登录原始返回、完整账号凭证和待选择会话保存在主进程内存。
- 下发页面的数据通过sanitize处理；只提供身份、交易指标等展示需要的信息。
- API身份解析优先级为 `futureInvestorId → futureUserID → futureUserId`。
- 详情中非null/undefined字段补充/覆盖登录信息，null/undefined不清除已有字段；**空字符串仍会覆盖**，不是自动保留所有非空登录值。未匹配账号保留。
- 多账号确认携带本次登录随机UUID `selectionToken`和 `accountKey`（优先id，后备索引），旧令牌不能用于新登录。
- 锁定用户、无账号、缺凭证、MAC不可用、管理端LinkID为空/读取失败会阻止进入主窗口。
- Binance初始化失败仅产生initializationWarning，仍进入主窗口以便诊断，不能误写成“初始化必成功才显示”。

### 4.5 管理端请求和页面安全

- 管理端请求通过Electron net.fetch及session cookies维持登录，`cache:'no-store'`。
- 成功同时要求HTTP成功和JSON `code="REQ_SUCCESS"`。
- 默认10秒中止计时，但计时器在fetch返回后清除，不是正文读取/解析全程硬10秒。
- 主窗口/登录窗口均启用contextIsolation与sandbox，禁用nodeIntegration。
- HTML使用本地脚本CSP和 `connect-src 'none'`，所有外网请求经过主进程。
- 当前没有全局错误data敏感字段清洗器，不能因正常账号sanitize就认为所有错误日志无泄露风险。

### 4.6 生命周期

- 主窗口加载完成后自动尝试连接账户事件，重复调用要复用连接。
- Windows窗口采用立即显示与加载完成兜底，避免只剩控制台没有主窗口。
- `ready-to-show`、`did-finish-load`、加载失败均有显示兜底；销毁窗口不能再操作。
- macOS关完窗口不自动退出进程，Dock激活时可以重新打开登录或主窗口。
- Windows关完全部窗口通常退出应用。
- `before-quit`清理计时器、未知订单查询任务、文件保存和网络客户端。
- **关闭程序不会自动平仓，也不会自动承诺账号没有持仓。**
- 当前没有完整“退出登录/换账号并清Cookie”的主界面流程。

### 5.2 当前代码使用的地址

| REST | `https://fapi.binance.com` | `https://testnet.binancefuture.com` |

### 5.3 环境切换链路

- 停止旧客户端的账户刷新、关键持仓刷新、管理端同步和Dead Man续期。
- 创建新环境客户端，绑定事件，然后关闭旧客户端。
- 清空最新延迟、账户和持仓快照；发布新范围“未确认”状态。
- 初始化新客户端并重新连接账户事件和后台任务。
- 页面清空旧市场快照、图表历史、自有挂单及相关显示，并重新连接当前全局合约。
- 主进程事件处理检查 `targetClient === client`，旧客户端晚返回不能跨环境发布。
- 本地订单/回合按环境和账号指纹过滤，不把测试网订单放到实盘。

当前管理端选定的凭证会被用于切换后的环境；管理端尚未返回明确的“该账号生产/测试凭证组”，因此不能假设切换环境会自动换一套API Key。

### 5.4 唯一全局合约

- 唯一交易对输入框为 `chartSymbolInput`，静态默认值为 `MUUSDT`。
- 通过按钮或对应页面事件切换行情。
- 输入规范化/后台校验后作为当前U本位合约。
- 表单下单、快捷键、行情查询、费率、成交、当前合约撤单等读取该全局来源。
- 已存在订单的撤单必须优先使用订单本身的 `symbol`，不能因全局合约后来改变而撤错合约。
- 全账号持仓/全部撤单/一键平所有不能缩小为只处理全局合约。
- 切换A到B会关闭A的深度和成交流，后台通过连接/合约身份检查忽略旧A数据。
- 账户事件仍是全账号订阅，可能继续收到A的订单/持仓事件，这是正常且必须保留的行为。
- 当前 `getSelectedSymbol()`直接读取输入框：**仅键入B、不点击切换时，图可能仍是A，但操作已经读取B**。这是需要后续补强的现有边界，不能理解成键入即完成订阅。
- 合约格式为大写字母数字、5–20字符，不接受现货式 `A/USDT`展示名。

## 6. 行情订阅与最新成交价

### 6.1 部分深度流

- 当前模式为 `partial`，订阅 `<symbol小写>@depth5@100ms`、`@depth10@100ms` 或 `@depth20@100ms`。
- 默认20档，`setDepthLevels()`同时改变显示档数和实际订阅档数。
- 当前每侧至多收到所选档数；不是买卖两侧合计20档。
- 每次部分深度消息构成当前有限档快照，不下载/维护默认1000档REST订单簿。
- 按Binance原生流的档位顺序取前N档（通常买盘价格降序、卖盘升序），保留消息实际数量；基础normalize不额外排序重建完整簿。
- 档位切换需要重新连接相应流，并清空当前连接的历史观察数据。
- `100ms`是服务器推送频率参数，不是程序必须再等100ms才渲染，也不是网络往返耗时。
- 当没有盘口变更或网络拥塞时，不保证严格每100ms都有一条消息。
- 基础代码当前接受 `100ms/1000ms` 两个配置字符串；默认与现有回归基线是100ms，不能把1000ms的接受校验当成所有Futures节点都支持该频率的证明。

### 6.2 最新成交价独立订阅

- 深度与最新成交价来自两个不同的WebSocket流。
- 最新成交价来自 `<symbol>@trade`，不是深度流中的买一/卖一价格。
- 后台保留最新成交价缓存，按总价市价下单尽量复用。
- 价格缓存过旧时底层查询ticker作为换算参考；不是永久使用旧成交价。
- 每笔原始成交不都跨IPC发给页面；`createLatestUpdateCoalescer`按32ms窗口只推最新值。
- 页面再结合 `requestAnimationFrame` 合并绘制，避免高频成交造成多余重绘。
- 这种合并用于“最新状态显示”，不是账户真实成交记账，不能应用到订单成交增量而丢交易。

### 6.3 连接和重连

- 手动断开后停止自动重连。
- 非手动断线按递增延迟重连，深度和成交连接分别维护。
- 切换合约时关闭两条旧流并清理重连任务。
- 深度关闭、断线、重连或进入新连接时清空图中历史价位，以免旧观察值冒充本连接数据。
- 主程序收到深度后通过 `onDepthUpdate` 驱动图表；修改IPC名、消息结构或脚本加载顺序时必须回归图表。
- 页面最新价格缓存没有年龄检查且断线不清空；快捷键和自动填价可能仍使用断线前的旧值。底层总价换算的10秒缓存规则不能自动保护所有前端限价计算。

## 7. 主行情图与历史价位

### 7.1 自定义Chart

原来位于renderer中的自定义工具类已独立到 `src/chart.js`，使用全局 `Chart`，并支持Node单元测试。

- 横轴表示价格，价格100.10的位置绘制该价位数量柱。
- 纵轴/柱高表示手数，视觉缩放由 `CHART_CONFIG` 决定，不等于屏幕像素与手数1:1。
- 基础价格小刻度当前硬编码为 `0.01`，不是所有合约都按 `tickSize` 动态改变画布刻度。
- 底层下单仍按Binance `tickSize/stepSize`校验，不能把图表刻度当成交易精度。
- `render()`保留背景、数量柱、自有挂单和回合成交覆盖层。
- 当前深度档数传入动态 `DepthLevelCount`，不硬编码只画10档。
- 绘制时不能因一次接收20档就无意删除用户要求的历史观察价位。
- 初始尺寸980×300，普通窗口resize约200ms防抖后按 `max(240, innerWidth - 80)`调整宽度，高度保持300。
- 当前数量高度是分段尺度，配置volumeScaleType=2；典型段为10/20/30/50/100/200/400/500，超过最大档有溢出高度。
- 主render中高低价/限制价/时间等若干方法调用仍被注释，不能把“类里有方法”写成可见功能已启用。

### 7.2 当前深度与历史深度

每个价位应区分：

- **当前档位**：最新部分深度快照包含的价位，实色。
- **历史观察档位**：本次连接曾经看到、现在移出5/10/20档的价位，半透明。
- **零数量**：明确收到数量为0时清除该侧历史记录，不能继续保留为有效量。

历史记录保留的是“这个价位最后一次实际观察到的数量”，不是完整历史逐笔行情，也不是此刻真实未变的全深度订单簿。

当前主图配置：

```js
{
  depthRetentionMode: "history",
  historicalDepthOpacity: 0.5,
  maxHistoricalDepthEntries: 10000
}
```

- 买卖两侧分别维护历史，不把买盘数量累加到卖盘。
- 每帧更新同价位最后观察值，不把同一价位连续快照误当累计成交量。
- 每侧当前快照覆盖价格区间内，旧有但本帧缺失的价位会清理；覆盖区间外保留最后观察值。
- 历史买价越过当前买一、历史卖价越过当前卖一时不会继续绘制，以免出现反向旧深度。
- 有条数上限，避免持续运行内存无限增长。
- 切换合约、环境、深度档位和断线重连时清空本次连接历史。
- 历史深度只在内存保留，不保存到本地JSON，不在重启后还原。

### 7.3 自有未完成订单

- 页面 `openOrdersByKey` 维护已确认未完成委托。
- 状态Map接受 `NEW`、`PARTIALLY_FILLED`、`PENDING_CANCEL`且剩余量大于0；当前Chart柱实际筛选NEW/PARTIALLY_FILLED，待撤状态可能仍在表格但不画柱。
- 横轴按委托价格，柱高按 `origQty - executedQty`，不是一直显示原报单量。
- 相同显示价位可以汇总绘制；“图内价位数”不必等于原始订单笔数。
- 同价同方向汇总；同价双方向分割柱宽，最小可见挂单柱高4px。
- 自有挂单用鲜红色/描边，与买卖深度区分。
- 没有有效委托价的条件单按可用触发价处理，实际显示仍受画布范围限制。
- 在可视范围外的订单不能消失于数据对象，只是不绘制在当前画布内。
- 接收确定订单状态后立即重绘两张图，不等待下一帧深度推送。
- 提交中不先画假订单；点击撤单也不先删除，等待Binance返回或账户事件。
- 较旧ACK和较旧查询快照不能把已经终态的订单重新放回图中。

### 7.4 回合成交和盈亏横条

- 当前合约的最新进行中回合提供成交覆盖层。
- 剩余方向为多时取多向平均成交价，为空时取空向平均成交价。
- 数量取回合 `remainingQty`；覆盖层不是直接来自所有仓位的全局净额。
- 已完成回合或缺少可靠平均价时清除覆盖层。
- Chart保留已成交位置和价格盈亏/方向横条绘制，缩放图也有同源覆盖层。
- 这些横条属于图表的价格差/回合辅助展示，不是Binance账户实际盈亏指标。
- 多向比较当前买一，空向比较当前卖一；盈利红、亏损蓝、同格绿，不包含费用、杠杆或金额PnL计算。

### 7.5 鼠标下单

- **主图的有效买卖侧价位双击**触发下单；不是单击、mousemove、页面任意双击。
- 通过Canvas真实边界、缩放比例和坐标解析方向/价位。
- 非画布事件、绘图区外、无有效行情/非正价、买卖价差区不能下单；当前不要求点击格有最新深度数量，买卖侧空格/历史格也可能有效。
- 使用“下单”窗口的数量或总价设置，构建LIMIT/GTC请求。
- 当前有 `chartOrderBusy` 与800ms冷却保护，一次只提交一笔。
- 鼠标价格标记条不能拦截Canvas双击，相关CSS/DOM更改要回归。
- 触发来源记录为鼠标来源，订单仍进入统一状态存储与确认链路。
- 主图双击沿用表单数量/总价与仓位动作，但覆盖为LIMIT、点击方向/格价、GTC，并清空触发/跟踪参数；没有额外逐单确认。
- 图表busy与快捷键busy各自独立，不是覆盖三个入口的全局单笔锁。
- **缩放图不具有鼠标下单功能，不得因复制Chart事件监听而意外恢复。**

## 8. 缩放行情与横轴聚合

### 8.1 聚合定义

- 第二个窗口名称“缩放行情”，位于原行情下方。
- 可选1、5、10级，默认1级。
- 只聚合**当前实际收到的5/10/20档快照**，不额外订阅更多深度。
- 基础步长0.01；聚合步长=`0.01 × 级别`。
- 区间左开右闭，价格映射到区间上边界，等价于精确十进制向上归桶。
- 买盘和卖盘分别加总，不能相互抵消。

| 级别 | 每个小刻度步长 | 示例区间 → 桶价格 | 每10个小刻度的标注间隔 |
| --- | --- | --- | --- |
| 1 | 0.01 | `(100.00,100.01] → 100.01` | 0.10 |
| 5 | 0.05 | `(100.00,100.05] → 100.05` | 0.50 |
| 10 | 0.10 | `(100.00,100.10] → 100.10` | 1.00 |

示例：5级下，买盘100.01数量2、100.03数量3、100.05数量4，显示100.05数量9。100.00恰好在桶边界，应留在100.00，不进入100.05。

### 8.2 当前快照与历史聚合

- `depthAggregation.js`使用BigInt十进制归桶/求和，避免 `100.05` 附近浮点边界误差。
- **先聚合本帧当前快照，再维护聚合价位历史**，不先把全历史原价位重算为“当前档位”。
- 原价位移出当前深度后，缩放图保留的是上次观察到的聚合桶值，半透明显示。
- 主图与缩放图各维护自己的历史价位Map。
- 改缩放级别时清空缩放历史并按新步长重建，避免5级与10级旧桶混杂。
- 改缩放级别不应改变主图订阅、主图刻度和主图历史。
- 切换合约/环境/档位/断线重连时，两张图都清空本次连接历史。

### 8.3 继承的展示能力

- 深度数量柱、历史半透明柱、最新成交价。
- 已确认自有挂单鲜红色柱，显示价格也映射至聚合桶。
- 回合成交覆盖层和盈亏/价格横条，价位同步归桶。
- 鼠标查看价位标记可保留，但无下单事件监听。
- 状态区显示当前级别、步长、买卖原始/聚合档数、挂单可视价位数量。

聚合后桶数可能少于原始档数，这是正常现象；聚合不会增加服务器推送的真实深度范围。

## 9. 杠杆查询设置与保存

### 9.1 作用层级

杠杆是Binance服务器上“当前账号 + 合约”的配置，**不是每笔订单的 `leverage` 字段**，也不是每次下单前都重新设置。

- 选择20倍后，下单手数不自动乘20。
- “按总价”仍表示名义金额，不是保证金金额。
- 开多/开空不各存一套倍率；当前是单向持仓。
- 设置一次并确认后，后续正常报单不增加一次设置杠杆的网络往返。

### 9.2 查询

切换全局合约时后台并行查询：

- `GET /fapi/v1/leverageBracket`：合约/账号风险档位。
- `GET /fapi/v1/symbolConfig`：当前服务器杠杆。
- 本地缓存通过独立IPC快速读取，只用于“本地Nx，校验中”展示。

UI从风险档位的 `initialLeverage` 最大值生成1到最大值的连续整数选项；底层通用格式限制1–125整数，但不是所有合约都能选125。

下拉框在 Binance 已确认的最大支持倍率后显示 `*`，例如 `50x*`；其实际选项值仍为纯数字，不改变当前选中倍率。仅本地缓存回显、尚未确认合约上限时不加星号；切换合约和修改倍率后继续依据当前合约已确认的上限标记。

Binance当前值覆盖本地值，并保存这次查询确认的结果。本地缓存不会在启动时自动强制POST回服务器。

### 9.3 修改

```text
用户选择新倍率
  → 标记同合约设置中
  → 禁用倍率控件与下单/参数测试按钮
  → 主进程LeverageChangeGate登记
  → POST /fapi/v1/leverage { symbol, leverage }
  → 验证Binance返回的合约和实际倍率
  → 成功才写本地JSON
  → 更新控件并释放下单保护
```

- 相同倍率不重复设置。
- API失败不保存新倍率，并重新查询Binance实际值以处理不明确结果。
- Binance已生效而本地写失败：返回 `applied:true`，提示“已生效但保存失败”，不能谎称服务器失败。
- 查询/设置有symbol与revision检查，切换合约后的旧响应不能覆盖新下拉框。
- 账户 `ACCOUNT_CONFIG_UPDATE` 通知当前合约配置变化时重新查询校准。

### 9.4 下单保护范围

- 表单、快捷键、主图双击、参数测试共享渲染层保护。
- 主进程还对真实下单、测试、改单、撤单重报实施同客户端/同合约保护。
- 纯撤单和一键平所有保留风险处置入口。
- 设置另一个合约不应在底层永久阻塞所有合约。
- **当前只在明确“设置中”时阻止，不会因为初次杠杆查询尚未确认而禁止全部下单。**未确认时下单使用Binance原有倍率。
- 当前返回的 `maxNotionalValue`尚未用于本地下单额度预拦截，最终风险档位校验仍由Binance执行。
- 主进程杠杆门禁是本进程client×symbol内存状态，不是跨实例共享交易锁；已通过门禁而仍在异步准备中的订单，也不被完整锁住等待后续设置。

## 10. 下单窗口参数及数量总价模式

### 10.1 表单字段

| 字段 | 当前含义 |
| --- | --- |
| 方向 | BUY / SELL |
| 仓位动作 | AUTO、OPEN、CLOSE；CLOSE自动reduceOnly |
| 委托类型 | LIMIT、MARKET、STOP、STOP_MARKET、TAKE_PROFIT、TAKE_PROFIT_MARKET、TRAILING_STOP_MARKET |
| 下单模式 | 按数量 / 按总价 |
| quantity | 按数量时使用的交易数量 |
| quoteOrderQty | 页面内部“按总价”的名义计价金额，底层换算为quantity |
| price | LIMIT/STOP/TAKE_PROFIT限价；市场单会删除该字段 |
| 最新成交价选择框 | 选中后行情最新成交价持续填入price；未选中保留手填 |
| stopPrice | 条件触发价 |
| activationPrice | 跟踪止损激活价，可选 |
| callbackRate | 跟踪止损回调百分比，0.1–10 |
| 仅测试参数 | 当前环境order/test，不生成真实单 |
| 提交真实委托 | 当前环境真实创建委托 |

### 10.2 按数量

- 发送数量之前按 `LOT_SIZE.stepSize` 或市场数量过滤器修正。
- LIMIT等有price时按 `PRICE_FILTER.tickSize`向下对齐。
- `adjustments`返回修正记录，显示原值与实际发送值的差异。
- 使用正数、小数字符串和精确十进制运算，避免简单二进制浮点四舍五入。
- 非交易状态、非法方向/类型、缺必填参数、数量/价格超范围应明确报错。

### 10.3 按总价

U本位普通下单接口当前不直接发送 `quoteOrderQty`。程序按参考价换算：

`quantity = floor_to_step(名义总价 / 参考价格)`

参考价优先级：

1. 有效委托价 `price`。
2. 有效触发价 `stopPrice`。
3. 最近成交价缓存。
4. 必要时查询最新ticker。

- 普通LIMIT按总价：price既作为实际委托限价，也作为数量换算依据。
- MARKET按总价：price不发送，使用最新成交价等换算；实际成交金额受滑点影响，不保证恰好等于输入总价。
- 条件单按总价：以可用限价/触发价为参考，执行时仍存在价格与实际名义金额变化。
- 向下对齐step后实际名义金额通常小于等于以参考价计算的输入金额。
- 按数量与按总价不能同时发送。
- 返回 `orderSizing`包含mode、请求总价、参考价来源、换算数量等信息。
- 输入2400表示2400USDT名义金额，不会自动变成“2400USDT保证金 × 杠杆”。

### 10.4 仓位动作

- `OPEN`：普通开仓意图，不携带reduceOnly；禁止同时显式要求reduceOnly。
- `CLOSE`：强制reduceOnly，防止扩大或反向新开仓。
- `AUTO`：当前不是一个基于全仓位预测的完备智能开平分类器；未显式reduceOnly的普通BUY/SELL仍可能减少、翻转或增加单向净仓。
- `positionSide`使用BOTH；发现双向设置时先尝试切到单向。
- 已有持仓/挂单导致币安不允许切模式时提示用户处理，不强行切换。
- 因旧模式缓存出现 `-4061` 时刷新后仅重试一次，不能无限重发。

### 10.5 条件单及底层高级参数

- STOP、STOP_MARKET、TAKE_PROFIT、TAKE_PROFIT_MARKET、TRAILING_STOP_MARKET进入Algo Order路径。
- 普通LIMIT/MARKET走普通order路径。
- 底层支持 `workingType`、`priceProtect`、`priceMatch`、`goodTillDate`、`closePosition` 等部分高级参数及适用性校验，但主表单不是全部都有独立控件。
- `priceMatch`与显式price互斥；只适用于支持的限价类型。
- GTD需有效 `goodTillDate`，晚于当前至少600秒并截至秒精度。
- `closePosition`只适用于指定条件市价平仓，不能同时携带quantity/reduceOnly。
- Post Only在底层以GTX表示，不在本基线主表单中提供独立Post Only选择项。

## 11. 下单链路响应与交易安全

### 11.1 统一入口

```text
表单 / 快捷键 / 主图有效双击
  → submitOrderWithTradFiAgreement
  → 杠杆设置中保护
  → preload IPC
  → main: leverage gate + trackOrderCall
  → BinanceUnifiedClient.placeOrder
  → BinanceUsdMClient.prepareOrder
  → 交易规则/单向模式/精度/总价/LinkID/STP校验
  → 持久交易WS order.place或algoOrder.place
  → 安全条件允许时HTTPS Keep-Alive后备
  → 保存订单状态、回合实际成交增量
  → Binance响应/账户事件确认后更新页面
```

普通、快捷键和图表不能各自复制一套未带LinkID或未维护状态库的请求代码。

### 11.2 ACK

- 默认 `newOrderRespType="ACK"`，而不是RESULT。
- 当前主界面沿用默认ACK；底层调用方仍可显式传入其他newOrderRespType，不能宣称代码绝对禁止RESULT。
- ACK是当前订单提交请求的快速响应，不是最终成交结果。
- 已确认NEW、部分成交、FILLED、CANCELED等状态由后续账户事件/查询维护。
- 响应可能很简短，没有origQty等完整字段；不得仅凭 `ok:true`就绘制一个本地推测的NEW挂单。
- 已收到较新账户终态后，较迟到达的ACK不得覆盖终态。
- 后台与页面两层都保存/比较订单时间、身份和事件状态。

### 11.3 WebSocket未知执行结果

- 已发送真实委托后连接中断/超时：可能币安已经接受订单，只是客户端丢响应。
- `retrySafe:false` 与 `requestSent` 控制不能盲目HTTP重发。
- 错误中保留 `executionStatus:"UNKNOWN"`、订单尝试身份等信息。
- 主进程按clientOrderId启动有限次数查询确认。
- 当前查证延迟依次为150/500/1500/3000/8000ms，查询成功后停止；不是无上限后台重试。
- UNKNOWN不是成交、不是撤单，也不是保证未被受理。
- 用户或上层流程不应在UNKNOWN时直接换一个新clientOrderId再次下同数量。

### 11.4 LinkID

- 当前仅使用 `BINANCE_FUTURES_LINK_ID`，现货标识不再读取。
- 正常登录时优先从管理端系统配置读取；环境文件为后备。
- 底层生成：`x-{LinkID}-{唯一后缀}`。
- 未提供后缀时由毫秒时间戳与随机字节生成。
- 已有同前缀不重复拼接。
- LinkID限定字母数字；拼接后clientOrderId为1–36个允许字符。
- 普通订单与Algo客户身份按各自API字段映射，统一保持底层经纪商标识。
- 经纪商Code不是订单查询条件，也不是交易账号id。
- 没有配置LinkID且调用方没有传clientOrderId时，底层不保证自动生成ID；正常管理端登录要求非空Futures LinkID。

### 11.5 签名和接收窗口

- REST当前使用URLSearchParams编码查询参数，HMAC-SHA256签名，API Key放X-MBX-APIKEY。
- REST各动词的当前参数均在query，不是订单JSON正文。
- 默认recvWindow=5000，使用交易服务器校准后的timestamp。
- WS签名按参数名称排序，拼接key=value后HMAC；USD-M将timestamp/recvWindow规范为数字并重新签名。
- 签名参数和真正发送值必须一致；修改类型、编码或参数顺序时须增加回归测试。

### 11.6 STP

- 默认使用 `selfTradePreventionMode=EXPIRE_MAKER`。
- 目的：当新Taker单将与同自成交保护范围的旧Maker单相撞时，使旧Maker单过期，避免这次自撮合。
- 不是“所有同一主账号的子账号天然互相保护”；必须看Binance设置的tradeGroupId。
- `tradeGroupId=-1`通常只能按当前账号范围解释，不能保证子账号之间保护。
- 可配置 `BINANCE_FUTURES_EXPECTED_TRADE_GROUP_ID`对照校验并提示不一致。
- 当前返回与界面明确提示：代码按IOC/GTC/GTD判断 `apiEffective`，MARKET/GTX不在本实现宣称的保证范围。
- 不能因为字段填写了EXPIRE_MAKER，就承诺市价平仓、所有Algo类型或所有子账号绝不自成交。
- 被STP取消/过期的订单必须进入终态维护并从挂单图移除。

### 11.7 TradFi-Perps协议

- 正式环境可调用签署方法；Testnet明确拒绝误调用正式签署服务。
- 当前实现 `POST /fapi/v1/stock/contract`，使用已排序参数签名。
- 账户窗口提供“签署TradFi-Perps协议”入口。
- 下单遇到需要协议的特定错误时统一入口识别、提示签署，用户确认后签署并最多按受控流程再尝试原单。
- 协议签署属于有业务含义的外部状态变更，不能无条件在每次登录/每次报单重复调用。

## 12. 撤单改单和撤单重报

### 12.1 单笔撤单

- 可按orderId或origClientOrderId识别订单；主窗口orderId会在部分成功下单后填入。
- `cancelOrderResolver.js`从本地最近订单/已知状态解析对应symbol和身份。
- 全局合约变更后，撤单仍应根据目标订单本身的合约发请求。
- 普通单优先 `order.cancel`，安全回退DELETE `/fapi/v1/order`。
- 已知Algo单通过Algo撤单路径处理，普通订单找不到时可按规则尝试Algo查询/撤销。
- 确定CANCELED等终态进入状态库并立刻重画图；若结果不明确，不能先删柱。
- 查不到/已成交/已撤等返回需清晰展示，不能把0笔取消当成整个账号已空仓。

### 12.2 当前合约全部挂单

- “撤销该交易对全部挂单”只处理当前全局合约。
- 普通 `/fapi/v1/allOpenOrders`与Algo `/fapi/v1/algoOpenOrders`均需执行。
- 后续查询和账户事件更新本地/图表，不能仅修改一个HTML表格。

### 12.3 快捷键全部撤单

- 动作范围是当前账号所有已知/服务器查询到的U本位挂单，不局限当前图。
- 并行查询全账号openOrders和本地recentOrders，合并待撤目标。
- 按symbol分组后调用全合约撤单，并把普通/Algo身份纳入处理。
- 服务器查挂单失败时可保留本地已知目标并提示警告，不能静默说没有订单。
- `cancelAllOrderTargets.js`统一归集，避免曾出现的“已下单但symbols=[]”回归。
- 快捷全撤确认后立即更新已发现订单的挂单Map、当前挂单表和两张图；当前没有显式再调用全账号历史/openOrders刷新，订单记录表主要依后续账户事件或后台对账更新。
- 合并来源还包括实时tracked挂单与最近2分钟ACK，弥补ACK刚返回而远端openOrders暂未出现的窗口；终态或过期ACK不生成撤单目标。
- 单笔身份有多个可撤匹配时应拒绝猜测；已知终态拒绝重复，没本地记录仍可由手工请求交服务器判断。

### 12.4 单笔查询与改单

- 查询普通 `order.status`，必要时处理Algo身份。
- 当前改单修改数量newQty，需查询原订单来获取side、price等。
- Futures路径使用 `order.modify` 或PUT `/fapi/v1/order`。
- **当前不能承诺保留原撮合优先级，也没有严谨地限定newQty只能减少。**“减量改单并保留优先级”的界面文字是当前已知边界，不能写进功能保障。

### 12.5 撤单重报

- Futures当前实现为“先撤原单 → 再新建LIMIT单”。
- 不是原子的cancel-replace，可能第一步成功而第二步失败。
- 新单仍走LinkID、EXPIRE_MAKER、精度、杠杆保护与未知结果保护。
- 返回和UI需保留原单取消结果、新单结果与失败信息。
- 第二步失败时不恢复旧订单，也不能给用户显示原单仍挂着。

## 13. 快捷键配置与执行

### 13.1 设置窗口

- 一级“配置”菜单下有“快捷键”“提醒合约参数”“色盲模式”。
- 快捷键设置首先显示当前列表，不直接展示所有编辑控件。
- 表头：快捷键、动作、方向、超价、手数/总价、操作。
- 每行操作：编辑、删除。
- 左下“新增”打开与编辑一致的新增窗口；保存后新增规则。
- 编辑保存更新当前记录；删除后按键不再匹配；恢复默认写回默认规则。
- 当前删除、恢复默认以及快捷键交易没有额外确认窗口；不能无意增加频繁确认影响快捷操作，也不能宣称现有确认不存在误触风险。
- 新增/编辑必须通过完整列表验证，不能产生重复key/id。
- 动作“下单（按数量）”和“下单（按总价）”名称与内部值必须严格区分，编辑后不能退回“下单”。

### 13.2 当前可选按键和动作

- 按键集合当前为 `Numpad0`到 `Numpad9` 与 `KeyP`，不是任意键盘按键录制系统。
- 小键盘显示名称为 `Num 0`…`Num 9`，普通字母P显示 `P`。
- 下单动作可以选多/空、超价、数量或名义总价。
- 撤销和一键平所有动作不要求方向、超价、手数。

| 内部action | 页面名称 | 参数 |
| --- | --- | --- |
| ORDER | 下单（按数量） | direction、priceOffset、quantity |
| ORDER_QUOTE_TOTAL | 下单（按总价） | direction、priceOffset、quoteOrderQty |
| CANCEL_ALL | 撤销全部未成交订单 | 无数量方向 |
| CLOSE_ALL_POSITIONS | 一键平所有 | 无数量方向 |

### 13.3 默认规则和超价语义

当前默认配置记录如下：

| 按键 | 动作 | 方向 | 配置超价 | 数量 |
| --- | --- | --- | --- | --- |
| Num 1 | 下单（按数量） | 空 | +0.1 | 0.001 |
| Num 3 | 下单（按数量） | 多 | -0.1 | 0.001 |
| Num 5 | 撤销全部未成交订单 | — | — | — |
| P | 一键平所有 | — | — | — |

超价按方向解释，多方向基准价为当前合约买一价B，空方向基准价为当前合约卖一价A：

- 多方向：实际价格 `B + priceOffset`。
- 空方向：实际价格 `A - priceOffset`。
- 正负数自然参与计算，不要对负数再错误取绝对值。

例：买一99.9、卖一100.1时，多+0.1报100.0；多-0.1报99.8；空+0.1报100.0；空-0.1报100.2。

**因此当前Num 1默认配置+0.1实际是卖一价减0.1。**本地保存的用户自定义配置优先于默认。

### 13.4 执行行为

- 使用 `KeyboardEvent.code`识别物理小键盘，不把主键盘数字1/3/5混为一谈。
- 输入框、选择框、编辑对话框等操作时应避免误触交易。
- 当前目标为input/select/textarea/button/contenteditable、任一快捷设置对话框打开、Ctrl/Alt/Meta/Shift或repeat时不执行。
- 忽略按住产生的repeat/冲突修饰键等无效触发，保持防重复与busy保护。
- 下单快捷键固定LIMIT/GTC、OPEN，数量/总价来自快捷键自身配置。
- 会更新下单窗口方向、类型、模式和价格，方便查看实际意图。
- 当前合约尚未收到对应方向的买一价或卖一价时，明确拒绝快捷键下单。
- Num5查询账号全部挂单；P是全账号平仓，不受画布合约限制。
- 快捷键保存到JSON并有旧版localStorage设置迁移，不只存在于浏览器内存。

### 13.5 其他菜单

- 系统：打开另外两份、重新加载界面、关于。
- 提醒合约参数：当前为提示说明入口，不是完整后台合约提醒引擎。
- 色盲模式：变更页面颜色/状态展示并使用localStorage保存开关。
- 色盲开关不应改变真实交易方向和订单状态。
- 普通深度颜色粉/绿，色盲深度红/蓝；鲜红挂单与回合盈亏横条不随开关改变业务含义。

## 14. 订单状态与最近24小时对账

### 14.1 三种不同的订单视图

| 对象/窗口 | 作用 | 范围/寿命 |
| --- | --- | --- |
| 页面openOrdersByKey | 即时挂单和图表 | 当前账号内存未完成订单，画图按当前合约过滤 |
| RecentOrderStore | 最近订单状态持久化 | 当前环境/账号滚动24小时，含终态与未知尝试 |
| Binance服务器查询 | 对账权威来源 | 依接口、时间范围、symbol和返回上限决定 |

不能只更新其中一个对象而不通知另外的消费者。

### 14.2 页面挂单Map

- 当前键是 `symbol:orderId`，例如 `MUUSDT:987654`，已经不是早期的 `市场:合约:ID`。
- `openOrderState.js`是统一normalize/update/key实现，调用方不应手写不一致的key。
- 支持终态集合：FILLED、CANCELED/CANCELLED、REJECTED、EXPIRED、EXPIRED_IN_MATCH。
- 终态按订单ID或clientOrderId移除匹配记录。
- WeakMap中的终态墓碑保留至多5000条，防止较旧NEW/快照使撤单柱复活。
- 新鲜度比较先看updateTime，再看receivedAt。
- 当前key不区分普通/Algo同数值ID，这是已知命名空间边界。

### 14.3 持久化对象

`RecentOrderStore.orders`为Map，持久键包含：

`environment:accountFingerprint:futures:symbol:order|algo|client身份`

主要字段：

- 环境、账号指纹、市场、合约。
- orderId/clientOrderId/actualOrderId、algoOrder。
- side/type/timeInForce/status。
- price/stopPrice/origQty/executedQty/cumulativeQuoteQty/averagePrice。
- positionSide/positionEffect/reduceOnly/closePosition。
- createdAt/updatedAt/observedAt。
- source/submissionSource、terminal、statusHistory。

- 金额和手数尽量使用字符串。
- 占位ACKNOWLEDGED/UNKNOWN不能覆盖已经确认的状态。
- 状态历史最多保留32次变化。
- 后续有更晚明确状态并不意味着持久库绝对“终态粘住”；严格防旧挂单复活由页面终态墓碑提供。client身份与orderId身份当前也不会无条件自动迁移成一条记录。
- 提交来源应在后续事件/查询后仍保留，用于定位误报单。
- `prune()`按最后活动时间updatedAt（fallback createdAt）清理24小时外记录，不严格按最初下单时间。
- 较早下的长期挂单可能不在24h本地库，但仍必须由openOrders和持仓安全查询处理。

### 14.4 全账号订单刷新

- 页面订单记录刷新调用 `syncRecentOrders()`，再显示状态库。
- 优先尝试不传symbol查询 `/fapi/v1/allOrders` 的24h窗口。
- 服务要求symbol时，回退“本地已知、使用过、当前和挂单发现的合约”逐个补查。
- 普通订单与Algo历史/挂单都纳入统一维护。
- Algo挂单全市场发现默认约5分钟一次，对已知合约补Algo历史；未知且没有任何已知记录/挂单的合约历史可能无法发现。
- 查询达到limit时按时间二分继续补齐，不静默截断首批。
- 本地过滤只显示所选环境/所选账号，画布换合约不应让全账号记录表变为单合约。
- 同步失败时保留本地状态并显示失败或部分警告。
- `queryMode`和warning必须留在状态文字，不把“已知合约回退”宣称为绝对全市场历史完备。
- 单个账号接口不能查询其他子账号；每个账号需要独立凭证与独立同步。

## 15. 实时账户事件与自动刷新

### 15.1 订阅

- 主窗口打开后后台自动调用连接账户事件，不要求用户先点按钮。
- U本位通过listenKey REST创建/续期，连接private stream。
- 面板仍保留连接、断开、清空事件按钮。
- 手动断开后不会自动偷偷重新连接，直到再次连接/相应生命周期触发。
- 非手动断线自动重连；listenKey失效需要受控更新。

### 15.2 事件规范化

- `ORDER_TRADE_UPDATE`被规范为程序内部 `executionReport`。
- `ALGO_UPDATE`、`CONDITIONAL_ORDER_TRIGGER_REJECT`也统一成订单状态事件。
- 保留 `rawEvent`以便识别原始U本位事件。
- `executionReport`在本程序中不代表仍使用现货接口，它是内部兼容事件格式。
- `TRADE_LITE`是更早的精简成交信号，只触发持仓失效和立即复核，不凭它估算手续费或已实现盈亏。
- `ACCOUNT_UPDATE.a.P`用于持仓增量；账户收益字段按各自规则入账。
- `ACCOUNT_CONFIG_UPDATE`用于杠杆状态校准。

### 15.3 实时消费者

每笔完整订单事件需要：

1. 更新RecentOrderStore。
2. 按累计成交量差额更新TradingRoundStore。
3. 按成交ID/事件身份去重更新收益和手续费。
4. 更新页面openOrders Map、当前挂单表和两张图。
5. 成交时让旧持仓快照立即失效，并启动0ms关键持仓查询。
6. 页面对订单记录和当前合约成交历史进行250ms合并刷新。
7. 展示事件列表及系统通知。

250ms是减少多事件重复查询的页面防抖，不是所有订单图形必须等待250ms。

### 15.4 重连对账和通知

- connected/reconnected后立即触发关键持仓与账户资金刷新，历史收益对账并行。
- 约750ms后执行最近24h订单对账，补偿断线期间遗漏。
- 通知包含“时间”“事件类型”“状态”；点击通知恢复/聚焦主窗口。
- 通知依赖操作系统通知支持和权限，不是强制阻塞式alert。
- 所有事件都可进入通知流程；当前没有针对高频交易的完整通知节流设置。
- 清空事件列表只清展示，不清订单状态、持仓或回合。
- 事件列表最新在上、最多100行内存展示，重启不恢复这份表格。

## 16. 交易回合和多空平均成交价

### 16.1 核心定义

- 以“环境 + API Key账号指纹 + U本位 + 合约”为配对范围。
- 按**实际成交增量**计算，不按下单原手数，不按ACK，不按未成交挂单。
- 多向：开多 `OPEN_LONG` + 平空 `CLOSE_SHORT`。
- 空向：开空 `OPEN_SHORT` + 平多 `CLOSE_LONG`。
- 多空累计手数一致则 `COMPLETED`；否则OPEN并记录待匹配方向/数量。
- 同范围有进行中回合时先匹配该回合，超出的成交量新建回合。

### 16.2 用户四种情况

| 原进行中回合 | 新成交 | 结果 |
| --- | --- | --- |
| 没有A | A空向10 | 新建A：多0、空10，待多10 |
| A空向5 | A空向10 | A空15，待多15 |
| A多向15 | A空向10 | A多15、空10，待空5 |
| A多向5 | A空向10 | 原回合多5空5完成，剩余空5建立新回合 |

上述“空向10”可以来自开空或平多；多向也可以来自开多或平空。该归类使用明确positionEffect、reduceOnly/closePosition等信号。

### 16.3 数据设计

- `TradingRoundStore.rounds`为数组。
- `executionCursors`保存每个订单累计已处理的成交量和成交金额，用于增量去重。
- `nextCreationSequence`使同一毫秒的新回合仍有稳定顺序。
- 订单身份优先actualOrderId，避免Algo触发后普通订单重复记账。

主要回合字段：

```text
id / creationSequence
environment / accountFingerprint / marketType / symbol
status / createdAt / updatedAt / completedAt
openLongQty / closeShortQty / openShortQty / closeLongQty
longQty / shortQty
longQuoteAmount / shortQuoteAmount
longAveragePrice / shortAveragePrice
remainingDirection / remainingQty
orderIds / executionCount
```

### 16.4 多空加权均价

- 多向平均价=`多向成交总价 / 多向总成交手数`。
- 空向平均价=`空向成交总价 / 空向总成交手数`。
- 不是简单平均每个订单的价格；优先真实累计成交额/成交价，而不是直接取委托price。
- 新增部分成交以累计量差额记账，优先用累计成交额/均价或本次真实成交价。
- 当前金额解析最后仍存在订单price/p后备；只能得到后备价格时，均价可能不是真实成交价，不能宣称所有旧数据均价已被交易所逐笔证实。
- 单次成交跨回合拆分时同步按成交量拆分成交金额。
- 缺可靠成交金额时相关均价保持未知/null，UI显示“-”，不输出误导性的0或部分平均价。
- 旧版回合可用订单累计成交额回填；跨回合成交必要时查询真实逐笔成交恢复各回合均价。
- 后台每次价格回填有最多200个订单引用的工作量上限，避免启动时阻塞。
- 回合和游标写入JSON，重启/重复账户事件/订单对账不重复记账。
- 显示按createdAt降序，同毫秒按creationSequence，最新在最上。

### 16.5 不能替代持仓检查

回合数据库可能没有覆盖：程序首次启动前的仓位、其他终端交易、24h之外未补齐历史、丢失/损坏本地文件和凭证指纹变更。

因此“某回合完成”不能证明Binance当前账号没有仓位。休息前必须看第18节的最新完整持仓确认；这是安全要求，不是对回合功能的否定。

## 17. 账户资金盈亏手续费及同步

### 17.1 数据权威和范围

- 管理端提供用户/账号身份：id、账号名称、API身份、Secret、代理代码、强平线等。
- 所选账号staticBalance、balance、available、positionProfit、closeProfit、realProfit、commission等动态交易值来自Binance。
- 没有登录并选中所有账号逐一查询的后台任务，因此不能把当前账号指标当成所有子账号实时总和。
- 币安原始数组/小数尽量严格校验，异常不应直接映射成0。

### 17.2 当前指标定义

| 字段 | 当前来源/定义 | 注意事项 |
| --- | --- | --- |
| staticBalance | U本位钱包余额walletBalance | 软件定义的静态权益，不是独立查询“昨日静态余额” |
| balance | U本位marginBalance | 动态权益/保证金余额 |
| available | availableBalance | Binance可用余额，不用realProfit替代 |
| margin | totalInitialMargin等初始保证金 | 不等同于全部资金/持仓名义价值 |
| positionProfit | 未实现持仓盈亏 | 随价格和持仓变化 |
| closeProfit | 近24h REALIZED_PNL求和 | 已实现交易盈亏，区别于净实际盈亏 |
| commission | 近24h COMMISSION费用的展示汇总 | 费用与收益符号转换见实现 |
| fundingFee | 近24h FUNDING_FEE/SPECIAL_FUNDING_FEE | 资金费可正可负 |
| realProfit | 近24h REALIZED_PNL + COMMISSION + FUNDING_FEE + SPECIAL_FUNDING_FEE | COMMISSION手续费流水通常负数；不含未实现盈亏/全部钱包变动 |
| deviation | 当前固定0 | 隔结误差尚无独立计算 |
| openVolume | 当前非零仓位条数 | 是合约/仓位计数，不是历史开仓手数 |
| orderVolume | 已确认未完成委托计数 | 不一定等于24h委托总笔数 |

当前指标以USDT为主要统一币种。收到非USDT收益而不能完整换算时标记不完整，不静默忽略后声称完整。

### 17.3 近24小时收益

- REST历史对账使用 `/fapi/v1/income`，滚动时间范围是 `now - 24h` 到now。
- 成交账户事件的rp、n/N等字段用于即时增加已实现盈亏与手续费。
- 资金费账户事件按对应原因更新。
- 使用事件去重和income journal，防止重连/重复消息重复累计。
- 收益历史返回期间发生的新交易不能被历史旧结果覆盖。
- 历史中已经包含的实时交易不能被再加一遍。
- 目标是滚动24h；当前边界旧收益的退出主要发生在历史对账，可能滞后到下一次5分钟对账，不能承诺每秒精确剔除。
- 完整收益历史默认5分钟对账，不每2秒重新拉完整流水。
- 收益接口失败使用约30秒退避，并保留最后有效值/完整性提示。
- 历史最多100页、每页1000条；实时journal/去重资料最多48h，均不是无限长期交易数据库。
- ACCOUNT_UPDATE.a.B当前主要辅助资金费，不逐条完整重建staticBalance/balance/available；余额/动态权益/浮盈仍主要靠账户查询刷新。

### 17.4 刷新调度

- 账户/持仓轻量刷新默认2秒。
- 交易成交/ACCOUNT_UPDATE后可提前安排刷新，相关账户轻量查询通常500ms合并。
- 成交/TRADE_LITE后的关键持仓0ms调度，与收益历史分开，不能让持仓等慢历史。
- 账户刷新、关键持仓、历史收益、管理端同步分别有single-flight/版本保护。
- 慢请求返回前发生新状态时不得回滚新指标。
- 接口短暂失败保留最后一次有效资金、仓位或收益，并降级完整性。

### 17.5 顶部账号信息字段实际映射

- “账号”：管理端userAccount。
- 第一个“账户状态”：管理端锁定/账号正常状态。
- “当前账户”：所选futureUserName。
- 第二个“账户状态”：最近Binance接口延迟/连接结果。
- “手续费”：所选Binance账号近24h手续费指标。
- “当前账户盈亏”“实际盈亏”“总实际盈亏”：当前代码均显示所选Binance账号realProfit。
- “隔结误差”：固定0。
- “强平线”：登录会话thrRealProfit。
- “可用资金”：Binance available，不是realProfit总和。

所以当前“总实际盈亏”不是全部子账号实时总盈亏，这一点与较早需求措辞有差异，应在扩展前明确。

### 17.6 连接状态色彩

- `elapsedMs <= 70`：绿色“在线”。
- `70 < elapsedMs <= 120`：黄色“在线”。
- `elapsedMs > 120`：淡红色“在线”。
- 没有可用Binance响应的失败/超时、或没有有效延迟：深红色“离线”；success=false但已有数值HTTP/API status且耗时有效时仍按在线分级。
- 收到HTTP/API错误响应仍说明服务可达，可显示在线；在线不代表账号有权限或订单成功。
- 这里使用浮点边界，不存在70.5ms不归类的整数空档。
- 当前是最近接口结果，不是独立网络健康探测器，也没有完整“多久没有新延迟自动离线”的机制。

### 17.7 同步到新期管理端

登录会话建立后调用 **`PATCH /future/futureAccountTradingInfo`**，默认每2秒调度。这里按当前实现和测试记录实际HTTP动词，不能根据较早讨论误写成POST。

```json
{
  "id": 233,
  "staticBalance": 1000,
  "balance": 1005,
  "available": 800,
  "closeProfit": 5,
  "commission": 1,
  "deviation": 0,
  "margin": 200,
  "openVolume": 1,
  "orderVolume": 2,
  "positionProfit": 5,
  "realProfit": 4
}
```

上面仅为结构示例，数值不是实际账号数据。

- id来自所选账号的管理端id，不是user id或Binance订单id。
- 同步前取得轻量Binance指标；不完整则跳过本周期，避免把管理端覆盖成错误0。
- 慢同步不并发堆积；2秒是调度间隔，不保证每个请求严格2秒内完成。
- 同步错误显示状态，下一周期继续受控尝试。
- 环境切换/旧会话结果需要检查client/session身份。
- 同步HTTP正文当前不带environment字段；测试与正式使用同一管理端账号id时的后端隔离需另行确认。
- 管理端边界将金额字符串转为JavaScript Number；账号id为正安全整数，开仓/委托计数为非负安全整数。

## 18. 当前持仓与空仓确认

### 18.1 查询范围

- 查询当前所选API Key下全部U本位合约，不传symbol时不应只查画布合约。
- 只展示 `positionAmt != 0` 的仓位。
- 数量正负与positionSide共同用于方向/展示。
- 列表包含开仓均价、标记价、名义价值、未实现盈亏、保证金、杠杆和模式等。
- 挂单不等于持仓，持仓列表空也不等于不存在将来可成交的挂单。

### 18.2 快速接口与增量

- 新增独立 `positionRisk()`，优先 `v2/account.position`。
- 传输失效安全回退GET `/fapi/v3/positionRisk`。
- 对数组、symbol和十进制positionAmt严格校验，异常抛错。
- `refreshPositions()`独立于收益历史返回，不等待24h收益流水。
- 有效 `ACCOUNT_UPDATE.a.P`按symbol+positionSide合并开仓、增减仓和归零。
- 无效增量保留旧仓并标记不完整。
- TRADE_LITE/完整成交先使旧空仓确认失效，再立即复核。
- 完整刷新会交叉对比positionRisk与account.status发现的非零仓位；不一致时保留危险补充仓位并降级完整性，不能仅用一个空数组确认无仓。
- 有效增量需要有已完整确认的基础快照，不能仅收到一条增量就升级为全账号完整。

### 18.3 快照数据与新鲜度

重要字段：

```text
positions / complete
environment / accountName / accountFingerprint / futureAccountId
positionsUpdatedAt / updatedAt
knownOpenOrderCount
sources.futures { configured, ok, updatedAt, error }
positionInvalidationVersion / positionEvidenceVersion
positionConfirmationRequired / warnings
```

- 使用positionsUpdatedAt，不借用余额或收益更新时间“刷新”旧空仓证据。
- 当前新鲜度阈值为8秒。
- 同合约成交前发出的旧查询，晚返回时不能覆盖成交后新状态。
- 范围包含环境、账号指纹和管理端账号id，换号/换环境要重置空仓确认。
- 查询失败时可以继续展示上次已知仓位，但必须标记旧/待确认。

### 18.4 “已确认无持仓”条件

只有同时满足下列条件，页面安全状态才应显示已确认空仓：

1. 查询来源已配置且成功。
2. 返回完整有效U本位快照。
3. 快照在新鲜度窗口内。
4. 当前没有待复核成交失效标记。
5. 连续两次不同有效证据均为零持仓。
6. 没有已知未成交挂单。

其他情况分别显示有持仓、仍有挂单、待二次确认、已过期、查询失败/不可确认等提示。

这个状态仍依赖API权限和可见范围，不是交易所托管的绝对风险保证。用户在外部终端继续交易后应重新确认。

## 19. 一键平所有与断线自动撤单

### 19.1 一键平所有

- 当前默认P，也可以在快捷键设置中改到可选按键。
- 动作只处理当前选定Binance账号的U本位市场，现货资产已不在软件范围内。
- 同一客户端并发调用应复用/阻止重复平仓任务，不能叠加多批订单。
- 页面busy保护不得仅因旧本地空仓标记就永远拒绝再次查询服务器平仓。

一般流程：

```text
发起一键平所有
  → 查询账号挂单与持仓
  → 普通/Algo挂单按合约撤销
  → 对非零仓位生成反方向MARKET + reduceOnly
  → 有限并发提交
  → 等待并向Binance复查
  → 有残余则报告明细，本轮不无限重复发平仓单
  → 返回已完成/仍有残余/不完整/失败与详细进度
  → 页面再次更新持仓、挂单和订单记录
```

- 多仓用SELL，空仓用BUY。
- 市价平仓以减仓为目的，不使用普通OPEN反向下单来“猜测对冲”。
- 限流期间读取retry-after并等待，受总时间/并发上限约束。
- 切环境或客户端关闭后安全停止旧任务。
- 单合约失败不应隐藏其他合约的进度与残余。
- 市价平仓可能有手续费和滑点，也仍可能遇到最小数量、权限、模式或交易所错误。
- 一键操作成功返回不应绕过持仓窗口的连续有效证据确认。
- 默认并发4（允许1–8），总任务最长10分钟；复核等待序列为0/150/400/1000/2000ms。
- 编排要求至少两份成功零持仓快照并确认无挂单；当前loop查询失败不重置已有零仓计数，严格说不是“两次连续成功查询”。
- 主进程一键平仓期间暂停周期账户查询和管理端同步以让出请求权重，finally无论成功失败均恢复。
- 非verifiedFlat会返回不完整/残余明细；用户应在确认后再次触发处理残余，不因本轮报单成功就关闭客户端。

**当前平仓编排中仍存在异常account.positions可能被宽松解析为空的路径，不能把“一键平所有”当成完全无条件可靠保证；详见第24节。**

### 19.2 断线自动撤单 / Dead Man

- 在运行状态勾选启用，默认倒计时120000ms。
- 页面范围5000–600000ms，代码校验实际输入。
- 调用 `POST /fapi/v1/countdownCancelAll`。
- 后台心跳周期根据倒计时受控计算，默认约30秒续期。
- 停止续期后由Binance在倒计时到期执行该合约挂单撤销。
- 不是平仓，不会自动卖掉已有仓位。
- 当前绑定一个symbol，不等于全账号所有合约Dead Man。
- 手动禁用应发送倒计时0并停止续期；错误不能静默吞掉状态。
- 切环境、关闭应用时停止旧续期；剩余服务器倒计时如何处理需依据已发送配置理解。

## 20. 网络传输限流缓存与延迟

### 20.1 网络原则

- Binance使用系统网络路由；没有SOCKS5、没有内置WireGuard启动器。
- 本地→上海→东京→Binance路径的传播/转发时延不能由前端代码消除。
- 不关闭TLS证书验证，不把未校验IP当官方服务。
- 私有网络不意味着API往返必然低于70ms；服务处理、流控和返回还会占时间。

### 20.2 交易WS与HTTPS

- 持久交易WS复用连接，避免每单重复DNS/TCP/TLS。
- 普通下单、撤单、单笔查询、改单、账户与持仓等已实现的WS操作优先走WS。
- 并不是每个接口都有WS版本：allOrders/openOrders/income/leverage/listenKey等当前仍有REST路径。
- 真实下单会尝试等待WS连接就绪；连接失败但未发送时仍允许HTTPS后备。
- 因此当前不是“WS不就绪一律禁止下单”的绝对策略。
- 请求已经发送后的未知真实下单禁止盲目后备重发。
- 业务错误（余额不足、非法价格、权限等）不是传输失败，不因其改走HTTP再提交。
- HTTP使用Keep-Alive、LIFO空闲socket复用；当前maxSockets=16，maxFreeSockets=8。

### 20.3 正式公共行情跨平台后备

- 正式U本位公共REST默认macOS为Electron→curl→Node，Windows为Electron→Node→curl；最近成功传输优先复用。
- 代码含配置的CloudFront公共数据后备及Futures Host处理，不应用于带Secret的签名交易请求。
- Windows无须安装curl：优先使用内建Electron/Node网络能力。
- 可通过 `BINANCE_CURL_PATH`指定后备程序；共享代码通过platformSupport分平台解析。
- curl使用execFile参数数组，不拼接未经校验的shell命令。
- 网络方案更改需回归macOS和Windows公共行情、签名REST及WS连接。
- 收到有效Binance HTTP业务错误不再换公共传输重复请求；只有网络/连接失败才尝试下一个。

当前关键默认时间参数：

| 参数 | 值/含义 |
| --- | --- |
| Node HTTPS请求 | 10秒请求与socket超时 |
| 交易WS连接 | 10秒 |
| 交易WS单次请求 | 5秒 |
| 交易WS心跳 | 20秒ping，缺pong断开重连 |
| WS重连 | 从1秒增加至最大30秒 |
| Electron公共请求 | 默认6秒，最小1秒 |
| curl后备 | 连接5秒、请求15秒、进程20秒，至多3次 |
| 管理端请求 | 默认10秒fetch中止计时，正文解析不在完整硬上限内 |

### 20.4 时间与规则缓存

- 服务器时间按baseURL分别缓存，防止一个主机偏移覆盖另一个交易主机。
- 时间缓存TTL120秒，后台30秒同步，重复同步single-flight。
- 时间偏移使用请求前后本地中点估算。
- 签名时间戳应使用交易服务对应偏移。
- exchangeInfo采用全市场快照和按合约缓存；过期优先复用旧有效缓存并后台刷新，避免每笔下单等大JSON。
- 首次没有有效规则仍需要查询，不能完全跳过tick/step校验。
- 价格缓存最大年龄当前约10秒，过旧时按总价换算需重新取价。

### 20.5 限流协调

- 观察REST响应头和WS rateLimits里的有效权重/订单计数。
- 不接受负数占位值，例如 `-1/-1`，避免误判已经100%限流。
- 多实例在公共rate-limits目录各写自己的JSON快照，周期合并。
- 达到约90%阈值时暂缓非关键查询，为下单/撤单等预留容量。
- 收到429/封禁窗口后，关键操作也必须尊重等待，不以“关键”名义绕过。
- 平仓任务有额外限流等待/批次控制，不能无限并发所有合约。
- 共享快照是保护层，不是完备的请求预扣账、分布式限流或跨电脑协调。
- 同IP不同账号仍可能共享某些交易所限额，不能只用“每秒一单”推断不会流控。

### 20.6 操作耗时与单接口耗时

| 指标 | 计时边界 | 用途 |
| --- | --- | --- |
| 执行结果elapsedMs | main.safeCall开始到业务调用完成，performance.now | 一次功能操作，可能包含校验、等待连接、多个API |
| 页面“端到端耗时” | 当前直接格式化上述result.elapsedMs，没有另开renderer全链路计时器 | 名称不代表已经额外测入完整页面/IPC往返 |
| 底部接口延迟 | 每个被埋点的HTTP/WS请求或连接/心跳的开始到结束 | 查看实际API调用，包括后台任务 |

- 小数保留至3位，单位毫秒；高精度计时不代表时钟/网络绝对精确到微秒。
- 一次功能可能发多个请求，底部最后显示其中最近完成的那个，不是功能总耗时。
- WS ping/pong是连接往返探测，不等同于订单撮合确认耗时。
- 深度和trade单向推送没有“客户端发起请求→服务器返回”的统一往返计时，不应把它们伪装成订单RTT。
- 最新延迟按32ms合并推送，状态概览随延迟同步更新。
- 失败请求也应保留耗时/错误，不能只记录成功的快请求。

### 21.4 IPC调用契约

主页面暴露对象为 `window.binance`，多数invoke返回：

```json
{
  "ok": true,
  "elapsedMs": 12.345,
  "data": {}
}
```

失败：

```json
{
  "ok": false,
  "elapsedMs": 1000.123,
  "error": {
    "name": "BinanceApiError",
    "message": "错误说明（当前没有全局error.data敏感字段清洗器）",
    "status": 400,
    "code": -1000,
    "data": {}
  }
}
```

- 名称、data结构、错误含义和耗时是页面契约，不能只修改后台返回而不改全部调用者。
- 特殊辅助API不保证每项都有相同外壳，修改前看当前handler。
- 订阅 `onX(callback)`返回取消监听函数，新增监听需考虑生命周期与重复注册。
- 页面禁止使用Node require/读文件/Secret签名。

- appData/userData的真实绝对目录由Electron决定，macOS与Windows不同。

- 修改数据结构必须有version迁移、旧文件测试和失败时保留原文件的策略。

### 22.5 杠杆持久化

- 账号范围优先管理端futureAccountId，fallback API Key非敏感指纹。
- 本地设置使用文件锁和锁内读盘合并，减少多实例覆盖其他账号记录。
- 环境必须testnet/production，symbol规范化大写，倍率1–125整数。
- 锁超时、写盘失败应返回真实错误，不能撤销已在Binance生效的倍率。
- 其他实例读时合并新记录，但不是主动实时UI广播；仍以Binance校准。

### 22.6 多实例与平台约束

- “打开另外两份”生成唯一 `--binance-instance=`参数，启动独立Electron进程。
- 各实例userData分离，避免本地订单/回合文件与页面session互相直接覆盖。
- 快捷键、杠杆及限流刻意共享，修改时不能误改成每实例一份或全部共享。
- 每个实例仍独立登录，可能选同账号或不同账号。
- 同一账号的不同实例能通过Binance账户事件观察对方交易，但本地回合数据库不是强一致共享数据库。
- 只有附加instance参数的实例有专用userData；手工多个普通进程若共用默认userData，仍有文件竞争边界。
- shared runtime不能无条件调用 `/usr/bin/...`、zsh、bash、.app路径。
- 子进程使用command+args、shell:false，Windows窗口隐藏控制按平台处理。
- 打包macOS多开由平台分支使用 `/usr/bin/open -n`；Windows直接启动exe；开发启动直接使用Electron。此mac专属路径不能移到无平台判断的共享分支。
- 新增进程、网络、.env查找和多实例分支必须有darwin/win32测试。

## 24. 当前已知边界和不能承诺的能力

本节是根据代码审閱得到的边界，**不是本次已修复的项目**。后续可以在用户授权后逐项补强；不能为了“保留旧功能”继续把它们宣传成保障。

| 编号 | 当前边界 | 对开发和测试的影响 |
| --- | --- | --- |
| K-01 | 仅U本位，无现货/COIN-M/杠杆现货/SOR/OCO/FIX/SBE等 | 不得引用旧聊天或过时文案宣称存在 |

## 25. 后续修改流程与防功能丢失检查表

### 25.1 每次修改前

1. 阅读AGENTS、本说明、当前git状态和实际源文件，不只依赖历史对话摘要。
2. 列出受影响功能编号、入口、共享数据和事件消费者。
3. 说明本次有意改变的行为，以及哪些保持不变。
4. 涉及历史保留、默认环境、订阅档数、交易模式和确认策略，应先明确告知用户。
5. 先有当前行为回归测试再重构；涉及安全缺陷需要用新失败测试描述修复目标。

## 附录E：快速场景对照

| 用户观察/需求 | 当前应怎样解释 |
| --- | --- |
| 切换合约后旧合约还有账户事件 | 正常，全账号private stream持续订阅；旧合约公共深度不应继续进入新图 |
| 图上还有半透明很多价位，但接口只20档 | 正常，是本次连接历史最后观察量，不是额外实时全深度 |
| 缩放后不是20根柱 | 正常，多个当前档位合并成更少的桶 |
| ACK成功但图上暂时没有柱 | 等待完整NEW/查询确认；不允许用本地猜测原数量先画 |
| 撤单请求失败但之后订单消失 | 可能撤单已执行而响应丢失/随后终态到达，要按Binance状态查证 |
| 回合完成但持仓窗口还有仓 | 以远端持仓为准；检查初始持仓、历史覆盖、外部交易与本地回合范围 |
| 持仓表空但状态待确认 | 不足两份完整新鲜证据或有挂单/失败，不可直接退出当空仓 |
| 一键平所有报告残余 | 不能当完全平仓；查看原因，独立复核后再处理 |
| 顶部“在线”但下单401/余额不足 | 在线仅表示服务有响应，不表示交易权限/余额满足 |
| 总价100、杠杆20 | 程序下100名义金额，不是自动下2000 |
| 重启后收益正确、运行中有滞后 | 查看账户事件连接、完整增量、历史退避、5分钟纠偏和范围版本，不能简单改成每2秒拉全历史 |
| Windows无curl | 内置Electron/Node路径仍应可用，curl只是可选后备 |
| 只输入B没有切换，图仍A | 当前存在输入与连接范围未完全分离的边界；应先完成行情切换再交易 |
